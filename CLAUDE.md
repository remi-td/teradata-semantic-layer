## Current state (v0.4)

The catalog ships as a Python package **`semantic-catalog`** with a
FastAPI-backed web GUI, a pure-Python compiler/importer/exporter, and
an embedded MCP server. The SQL bundle is DDL + the two macros that
back `semantic.search` / `semantic.describe` — no SQL compiler, no SQL
importer, since v0.4.

### Known conventions

- DB identity values are surrogate integers generated by `GENERATED ALWAYS AS IDENTITY`.
  After insert, look up the new id by natural key (model_id + name) — Teradata doesn't
  have `SCOPE_IDENTITY()`.
- ANSI-mode sessions need explicit COMMIT/ROLLBACK. The import endpoint flips
  `conn.autocommit = False` for the duration of one batch and commits iff every
  entity reported OK and `dry_run=False`.
- DBC metadata is inconsistent: `dbc.TablesV.DataBaseName` (capital B) vs
  `dbc.ColumnsV.DatabaseName` (lower b). The catalog faithfully mirrors that.
- `DBC.SysExecSQL` is NOT callable from `demo_user` on the ClearScape sandbox —
  don't design EXPLAIN validators that rely on it. `/api/query/explain`
  handles this by running EXPLAIN directly from the driver instead.
- FastAPI + Pydantic v2 complains about `model_name` collisions ("protected
  namespace `model_`"). All the API Pydantic models set `model_config =
  ConfigDict(protected_namespaces=())` to silence this.

## Context

We are implementing a semantic layer metadata catalog that lives inside Teradata's own data dictionary. The catalog stores metadata about datasets (tables/views/queries), their fields (columns/expressions), metrics (aggregate expressions), relationships (joins), and semantic views (curated projections for agents and BI tools). 

The system supports incremental maturity: a user can register a "cube" (a flat query with labeled dimensions and measures) on day one, and progressively decompose it into a full relational model with explicit entities, keys, and relationships over time — without breaking anything.

The catalog must also support:
- Projection/export to OSI YAML
- An agent interface for discovering, requesting, and compiling queries from semantic metadata
- A SQL compilation engine that reads the catalog and generates optimized Teradata SQL with selective join pruning

## Task 1: Physical DDL

Create all tables in the `demo_user` database (the current user/database on this sandbox). Follow these rules precisely:

### Teradata DDL rules
- Always specify `MULTISET` (this is a metadata catalog, not a transactional system)
- Always specify `FALLBACK` for data protection
- Always specify `PRIMARY INDEX` explicitly — choose based on the most common access path
- Use `GENERATED ALWAYS AS IDENTITY` for surrogate keys
- Use `VARCHAR(128) CHARACTER SET UNICODE NOT CASESPECIFIC` for all name fields that may hold Teradata object names (matching dbc conventions)
- Use `COMMENT` on every table and every column — this is critical for agent discoverability
- Use `COLLECT STATISTICS` on PI columns, FK columns, and columns used in WHERE clauses
- Create unique indexes for natural keys

### Physical mapping alignment with dbc
- `dbc.TablesV` uses `DataBaseName VARCHAR(128)` (capital B in Base) and `TableName VARCHAR(128)`
- `dbc.ColumnsV` uses `DatabaseName VARCHAR(128)` (lowercase b), `TableName VARCHAR(128)`, `ColumnName VARCHAR(128)`
- DATASET entity uses `DataBaseName` and `TableName` (matching TablesV)
- FIELD entity uses `ColumnName` only (matching ColumnsV) — DatabaseName and TableName are inherited from the parent DATASET

### Entities to create (in dependency order)

1. **SEMANTIC_MODEL** — top container
2. **DATASET** — business entity (table, view, or SQL query)
3. **FIELD** — atomic unit (attribute or key), child of DATASET
4. **DATASET_KEY** — which fields form PK/UK (intersection of DATASET and FIELD)
5. **RELATIONSHIP** — join between two datasets (from_dataset → to_dataset)
6. **REL_COLUMN_MAP** — column pairs for joins (intersection of RELATIONSHIP and FIELD on both sides)
7. **METRIC** — model-level aggregate expression
8. **METRIC_EXPRESSION** — multi-dialect SQL for metrics (Teradata + ANSI_SQL)
9. **METRIC_FIELD_REF** — which fields a metric consumes (intersection of METRIC and FIELD)
10. **SEMANTIC_VIEW** — curated projection for consumers
11. **VIEW_MEMBER** — exposed dimensions/measures in a view
12. **AI_CONTEXT** — polymorphic agent metadata (instructions, synonyms, examples)
13. **FORMAT_SPEC** — polymorphic display formatting
14. **SECURITY_POLICY** — polymorphic access control
15. **CUSTOM_EXTENSION** — polymorphic vendor metadata
16. **DIALECT_ENUM** — reference table (ANSI_SQL, TERADATA)
17. **VENDOR_ENUM** — reference table (TERADATA, COMMON)
18. **FIELD_TYPE_ENUM** — reference table (A=attribute, K=key)
19. **METRIC_TYPE_ENUM** — reference table (SIMPLE, RATIO, CUMULATIVE, DERIVED)
20. **CARDINALITY_ENUM** — reference table (MANY_TO_ONE, ONE_TO_ONE, ONE_TO_MANY, MANY_TO_MANY)

Refer to the design document for exact column definitions, types, and keys.

### Validation
After creating each table, verify it exists by querying `dbc.TablesV`. After all tables are created, verify the full schema by querying `dbc.ColumnsV`.

- Format specs on revenue metrics (currency USD)

Since TPC-DS tables don't exist on this sandbox, use realistic DataBaseName/TableName references (e.g., `tpcds.store_sales`) but leave them as metadata-only — the physical tables don't need to exist for the catalog to work.

## Task 4: Agent Interface

Design and implement three stored procedures (or macros) that form the agent contract:

### 4.1 `sp_semantic_search`
**Purpose:** Agents search for business terms to discover what's available.

**Input:** A search term (VARCHAR), optional model_id filter.

**Behavior:** Search across field names, metric names, dataset names, AI context synonyms, descriptions, and display names. Return a ranked result set with:
- entity_type (DATASET, FIELD, METRIC, VIEW)
- entity_name
- parent_name (dataset name for fields, model name for metrics)
- description
- synonyms (from AI_CONTEXT)
- relevance (simple keyword match scoring)

### 4.2 `sp_semantic_request`
**Purpose:** Agents submit a structured query request.

**Input:** A JSON string representing the request:
```json
{
  "model": "tpcds_retail",
  "metrics": ["total_revenue", "customer_count"],
  "dimensions": ["date_dim.d_year", "store.s_state"],
  "filters": [
    {"field": "date_dim.d_year", "op": "=", "value": "2023"},
    {"field": "total_revenue", "op": ">", "value": "1000"}
  ],
  "sort": [{"field": "total_revenue", "direction": "DESC"}],
  "limit": 100,
  "execute": false
}
```

**Behavior:**
1. Resolve metric names → METRIC_EXPRESSION (Teradata dialect)
2. Resolve dimension names → FIELD expressions
3. Walk the RELATIONSHIP graph to determine which datasets need to be joined (selective join pruning — only include joins required by the requested dimensions and metrics)
4. Build the FROM clause with appropriate JOINs (using REL_COLUMN_MAP for join conditions)
5. Build SELECT with dimension expressions + metric aggregate expressions
6. Build WHERE from filters on fields (pre-aggregation) 
7. Build HAVING from filters on metrics (post-aggregation)
8. Build ORDER BY and TOP from sort/limit
9. EXPLAIN the generated SQL to validate it
10. If `execute = true`, run it and return results
11. If `execute = false`, return the compiled SQL only

**Output:** A result set with:
- compiled_sql (the generated Teradata SQL)
- is_valid (BYTEINT — 1 if EXPLAIN succeeded)
- validation_message (error text if invalid)
- result_json (JSON result if executed, NULL otherwise)

### 4.3 `sp_semantic_describe`
**Purpose:** Agents get the full description of a specific entity.

**Input:** entity_type (VARCHAR), entity_name (VARCHAR), optional model_name.

**Behavior:** Return all metadata for the entity: description, AI context, format spec, fields (if dataset), expressions (if metric), relationships (if dataset), view members (if view). Return as a structured result set that an agent can consume.

## Task 5: SQL Compilation Engine Design

Write a design document (as a markdown file) for the SQL compilation engine. Research and reference these open-source projects:

### Projects to study
1. **MetricFlow** (github.com/dbt-labs/metricflow) — Apache 2.0, Python. Uses a dataflow plan DAG for query compilation. Compiles metric definitions into platform-specific SQL. Key files to study: `metricflow/engine/`, `metricflow/plan_conversion/`, `metricflow/sql/`.

2. **Cube** (github.com/cube-js/cube) — Apache 2.0, Rust/JS. Query orchestration engine that resolves join paths from views. Key concepts: join graph resolution, pre-aggregation matching.

3. **dotML** (github.com/zurferr/dotML) — Apache 2.0, Python. Lightweight semantic layer. Simplest example of YAML → SQL compilation. ~500 lines of Python. Good reference for the minimal viable approach.

4. **Apache Calcite** — The underlying SQL planning framework. Julian Hyde's work on adding MEASURE as a first-class SQL concept. Long-term reference for native engine integration.

### Design document should cover:

1. **Architecture overview** — How sp_semantic_request works internally. The compilation pipeline stages.

2. **Join graph resolution** — How to walk the RELATIONSHIP table to find the minimal set of joins needed for a given set of dimensions and metrics. Algorithm: start from the metric's primary dataset, BFS/DFS to find paths to each dimension's dataset, prune unnecessary joins. Reference how MetricFlow and Databricks metric views do this.

3. **Expression substitution** — How metric expressions (which reference `dataset.field`) get resolved to actual SQL column references with proper table aliases.

4. **Filter classification** — How to determine whether a filter is pre-aggregation (WHERE) or post-aggregation (HAVING). Rule: if the filter references a metric name, it's HAVING; if it references a field, it's WHERE.

5. **Fan-out and chasm trap detection** — How to detect when a join path would produce incorrect aggregation due to fan-out. Reference how MetricFlow avoids this with entity types and how Honeydew handles it.

6. **Teradata-specific optimizations** — LOCKING ROW FOR ACCESS on read queries, COLLECT STATISTICS hints, PI-aware join ordering.

7. **Simplification strategy** — Given that we're implementing this inside Teradata (stored procedures + SQL), not as an external middleware, what's the simplest viable approach? The recommendation: implement the compilation as a recursive SQL procedure that walks the catalog tables, builds SQL strings, and validates via EXPLAIN. No external runtime needed. The catalog IS the engine.

8. **Future evolution** — How this could evolve toward a Teradata-native MEASURE() function (à la Databricks), MCP server integration for Claude/agent consumption, and OSI compatibility layer.

## Important conventions

- All table and column names use snake_case EXCEPT for physical mapping columns that match dbc conventions (DataBaseName, TableName, ColumnName)
- VARCHAR fields that hold names: `VARCHAR(128) CHARACTER SET UNICODE NOT CASESPECIFIC` (matching dbc)
- VARCHAR fields that hold descriptions: `VARCHAR(10000) CHARACTER SET UNICODE`
- VARCHAR fields that hold SQL expressions: `VARCHAR(32000) CHARACTER SET UNICODE`
- JSON fields: `JSON(32000)` or `JSON(64000)` for large payloads
- CLOB for source_query on DATASET
- BYTEINT for boolean flags (0/1)
- TIMESTAMP(6) for audit columns with `DEFAULT CURRENT_TIMESTAMP(6)`
- Always `COMMENT ON TABLE` and `COMMENT ON COLUMN` after creating each table
